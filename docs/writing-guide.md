# 読ませるページの書き方（調べたことと、このサイトの決まり）

このサイトの文章を書く・直す人のためのメモです。Web の読まれ方と、読みやすい文章について調べたことをまとめ、それをこのサイトでどう使っているかを書いています。

## 1. 調べてわかったこと

### 人は Web のページを「読まずに拾い読みする」

- ユーザビリティの研究で知られるヤコブ・ニールセンの 1997 年の調査では、利用者の 79% が新しいページを拾い読み（スキャン）し、一語ずつ読んだのは 16% だけでした。勧められていたのは、強調したキーワード、意味のある小見出し、箇条書き、一段落に一つの考え、結論を先に書く「逆ピラミッド」、ふつうの半分以下の文字量です。（[How Users Read on the Web](https://www.nngroup.com/articles/how-users-read-on-the-web/)）
- 視線の研究では、見出しと小見出しを拾い、気になったところだけ本文を読む「レイヤーケーキ型」の読み方が知られています。見出しがはっきりしていて、中身を表しているときに起きる読み方です。（[Text Scanning Patterns](https://www.nngroup.com/articles/text-scanning-patterns-eyetracking/)）
- 2018 年の調査では、ページを見ている時間のおよそ 74% が、最初の二画面に集中していました。（[Scrolling and Attention](https://www.nngroup.com/articles/scrolling-and-attention/)）

→ **見出しだけ、要点だけを拾っても話がわかるようにする。いちばん大事なことは最初の二画面に置く。**

### 結論を先に、文は短く

- 木下是雄『理科系の作文技術』（中公新書, 1981）は、大事なことを先に書く「重点先行主義」と、短い文で書くことを説いています。読む人が、続きを読むべきかをすぐ判断できるようにするためです。
- 日本語の読みやすさの研究では、文の長さと漢字の割合が大きく効くとされてきました。漢字が4〜5字以上続くと読みにくい、という目安もあります。

→ **章も段落も、結論から書く。一文に一つのことだけ。漢字が続いたら、ひらがなや言い換えで切る。**

### 問いかけと、身近な例

- 心理学者ローウェンスタインの「情報の空白」の考え方（1994）によると、好奇心は「知っていることと知りたいことの間のすき間」に気づいたときに生まれます。ただし、すき間が大きすぎても小さすぎても働かず、少しは知っていて、答えにたどり着けそうなときに強くなります。
- 抽象的な考えは、具体的な例と一緒に学ぶと理解しやすく、新しい場面にも当てはめやすくなることが、学習の研究で確かめられています（Rawson ほか, 2015 など）。

→ **問いかけは、読者が知っている身近なことについて聞き、すぐ後で答える。抽象的な話の前に、具体的な例を一つ置く。**

### 文字の組み方

- アクセシビリティの国際基準 WCAG 2.2 の達成基準 1.4.8（AAA）は、一行の長さを 80 字以内（日本語などは 40 字以内）、行間を 1.5 倍以上、段落の間をそれ以上にすることを挙げています。両端そろえも避けるよう書かれています。（[Understanding SC 1.4.8](https://www.w3.org/WAI/WCAG22/Understanding/visual-presentation)）

→ **本文は一行 36 字前後、行間は 2 倍前後にしている（`src/styles/global.css` の `.longform`）。**

## 2. このサイトの決まり

### ページの組み立て

1. **最初に、まとめを置く。** トップページの「設計会の考え方」は、各章の見出しと要点から自動で作られます。
2. **文脈から並べる。** 読む人は、前の章を前提に次の章を読みます。トップページは「設計とは → なぜ価値を決めるのか → なぜ今か → 学べるのか → 何を学ぶか → 誰と → どこで」の順です。知らない言葉や考えを、説明する前に使わないようにします。
3. **1 ページで伝えたいことは 1 つ。** 一つのページに話題が二つ以上あったら、ページを分けます（設計の工程は、1 工程 1 ページにしています）。分けたページどうしは、行き来しやすいようにつなぎます。
4. **章は「問い → 主張 → 要点 → 本文」の順。** 章の上の小さな文字（eyebrow）は読者が心の中で持っている問い、見出しはそれに答える主張、すぐ下に要点を置きます。
5. **見出しは主張の形で書く。** 「データ分析について」ではなく「数字は同じでも、形はまったく違う」。見出しを上から読むだけで、話がつながるようにします。
6. **大事さに合わせて見た目を変える。**

   | ブロック               | いつ使うか                                                               | 見た目                     |
   | ---------------------- | ------------------------------------------------------------------------ | -------------------------- |
   | `point`（要点）        | その部分でいちばん言いたいこと。拾い読みする人はここだけ読む             | オレンジの線               |
   | `question`（問いかけ） | 身近なことを聞いて、続きを読みたくさせる。答えは `answer` に（隠さない） | 「？」の印と、すぐ下の答え |
   | `example`（身近な例）  | 抽象的な話の前後に、具体的な場面を一つ                                   | 灰色の箱                   |
   | `heading`（小見出し）  | 章の中で話が切り替わるところ                                             | 黒い四角                   |
   | `aside`（補足）        | 本題ではないが分量の多い補足や、詳しい事例                               | 折りたたみ                 |
   | `p`（段落）            | 本文。一段落に一つの考え。短い補足や出典は `note` に                     | `note` は本文の右          |

7. **読み方を読者に説明しない。** 「3分で読める」「読み飛ばしてもよい」のような文は書きません。拾い読みしやすさは、見出し・要点・見た目で実現します。
8. **折りたたみは読まれにくい。** 折りたたみ（`aside`）は開かれずに読み飛ばされることが多いので、読んでほしいもの（問いかけの答えなど）は入れません。本題でない長い補足や、詳しい事例だけを入れます。短い補足や出典は、段落の `note`（本文の右）に書きます。
9. **主張には、実際にあった例を添える。** 例は出典を確かめ、`note` に出どころを書きます。数字が資料によって違うときは、控えめな方を使います。架空の例（部室の予約や、設計の流れの例のページ）は、架空だとわかるように書きます。
10. **イメージしにくいところには図を置く。** イラストは使いません。図は `src/components/figures/` に、機能の図は `idef0` ブロックで描きます。外部の画像は必要最低限にし、ライセンスを確かめて `docs/image-credits.md` に書きます。
11. **実例は、一つの主張に一〜二件まで。** 調べると例はいくらでも見つかりますが、並べすぎると主張が薄まります。いちばん強く、読者（岡山の大学生）に身近な例を選び、同じ例をほかのページで繰り返さないようにします。確かさが中くらいの例は使いません。
12. **関連授業は補足として添える。** 学内の授業とのつながりは親近感につながります。ページごとに五件まで、いちばん関係の深いものを選びます。
13. **設計会の趣旨から外れる話は足さない。** 調べてわかった面白い話でも、設計会の活動（実装の手前までの設計）につながらないものは、ページを薄くするので入れません。

### 想定する読者

頭のいい大学生です。やさしく書くことと、中身を薄くすることは違います。正しい用語、実際の仕組み、数字、手法の名前とその理由は省かずに書き、初めて出てくる用語はその場で言い換えます。

### 出典

- 出典は、必ずリンクを付けて書きます。URL のない出典は使いません。見つからないときは、その出典に頼る主張ごと書きません。
- 段落の注（`note`）、例の出典（`source`）、図の出典では `[表示名](https://…)` と書きます。参考文献（`references`）には `url` を書きます。
- リンク先は、DOI、出版社・規格団体・官公庁・博物館などの公式のページ、国立国会図書館サーチや CiNii の書誌を優先します。
- 図の出典にリンクがあるかは `npm run check:sources` で、文章の注や参考文献は `npm run build` で確かめられます。

### 文の書き方

- 言いたいことは、そのまま肯定の形で書く。「A を言うために『A でないことはない』『￢A ではない』と書く」二重否定や否定の言い回しは、遠回しで読む負担が増えるので使わない（例：「難しくない」→「やさしい」、「無駄にならない」→「役に立つ」、「迷わない」→「一目でわかる」）。
- 単語は正しい意味で使う。専門用語は、分野の定義（規格・教科書）に合っているかを確かめてから使う。
- 文脈を先に置く。章や段落は「なぜその話をするのか（前の話とのつながり）」から始め、用語は使う前に説明する。
- 一文は短く。読点（、）で三つ以上つながったら、文を分ける。
- 専門用語は、初めて出てきたところで言い換える（例：「要件（設計が満たすべき条件）」）。
- 「〜と言われています」は、出どころがはっきりしない数字に使う。確かめた数字は言い切る。
- 強調（`**…**`）は一段落に一か所まで。多すぎると、どこも目立たなくなる。
- 身近な例は、読者（大学生）の生活から選ぶ。授業の課題、サークル、アルバイト、家の中のもの。業界の話は補足に回す。
- 同じ言葉（「価値」「考え抜く」など）を何度も使わない。決め台詞は、ここぞという一か所だけにする。
- 問いかけの答えは、すぐ後に書く（答えはいつも見えている）。
- 読者を突き放す言い方をしない。たとえば「センスではなく論理」は、デザインを学ぶ人には「センスは要らない」と読める。「センスだけでなく」と書く。

### 「設計を知る」のページ

- 決まった章立てはありません。そのテーマが**いちばん伝わる順番**で書きます。多くのページは「身近な問い → 何なのか → なぜ大事か → どう使うか → いま → 設計会では → 寄り道（歴史）」の順ですが、合わなければ変えてかまいません。
- 新しいテーマは、`src/content/design/` に YAML を一つ足すだけで、一覧・地図・リンクに加わります。
  - 設計のプロセスの全体 … `layer: process`（「設計のプロセス」の一ページだけ）
  - 工程一つずつ … `layer: step`。`order` が工程の番号。ページの上に、ほかの工程へ移れる帯が出る
  - どの工程にも通じる視点 … `layer: lens`。`perStep` を書くと、地図の表に「工程ごとの使い方」が出る（書かなければ空欄）
  - 実際の設計の流れの例 … `layer: case`。章に `step: 番号` を書くと、工程のページへのリンクが付く
  - それ以外のテーマ … `layer: topic`

### 言葉と表記

言葉の使い方は、調べて確かめてから書きます。表記は文化審議会「公用文作成の考え方」（2022年）をもとに、読みやすさのために JTF 日本語標準スタイルガイドも参考にして決めています。

| 項目             | 決まり                                                                                                    | 例                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| ひらがなで書く語 | つくる・わかる・よい・ない・できる・こと・とき・もの・など                                                | 「作る」→「つくる」（試作・製作のような熟語は漢字）    |
| 漢字で書く語     | 今・一つ・繰り返す・仕組み                                                                                | 「いま」→「今」                                        |
| 「〜つ」の数     | 漢数字（一つ〜九つ）。ほかの数は算用数字                                                                  | 五つの工程、3操作、1,500倍                             |
| 4桁以上の数      | コンマで区切る                                                                                            | 1,500倍                                                |
| 英字             | 半角。前後の日本語との間に空白を入れない（出典の注と参考文献は除く）                                      | AIに頼む、IDEF0で描く                                  |
| 外来語の長音     | 語末の -er・-or などは「ー」を付ける                                                                      | コンピューター、プリンター、パラメーター、ライブラリー |
| よく揺れる語     | ウェブ（Web ではなく）、スマートフォン（スマホではなく）、使う人・利用者（使い手ではなく）                |                                                        |
| 設計の言葉       | 要求＝人の願い、要件＝確かめられる条件、工程＝設計の5つの段取り、段階＝製品の一生（開発・製造・運用など） | 「要件定義」（「要求定義」ではなく）                   |

確かめた言葉の例：構想設計（概念設計）は「案を広げる」と「比べて選ぶ」を合わせた範囲を指すので、工程3は「発想」と呼んでいます。CAE は構造だけでなく流れや熱などの解析全般を指します。2024年に義務になったのは、求められたときの「合理的配慮」で、ウェブなどの「環境の整備」は努力義務です。
